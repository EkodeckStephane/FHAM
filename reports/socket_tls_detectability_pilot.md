# Local TCP socket detectability pilot

## Design

This experiment compares a FHAM application exchange with a matched HTTP
control over real local TCP sockets. A transparent relay forwards the live
TCP byte stream between client and server and records only byte counts,
TLS-record lengths, read-chunk sizes, and arrival times. TLS is end-to-end
between the client and server; the relay does not terminate it. No application
payload or ciphertext is written to the result files.

The positive FHAM exchange uses the authenticated session and AES-GCM record
implementation in the repository. The HTTP/1.1 JSON control has exactly the
same plaintext request and response byte lengths as its paired FHAM exchange.
Both use the same local endpoints, client/server code, and TLS 1.3/OpenSSL
configuration. Each request and response is sent in one application write.
The experiment includes both raw TCP and TLS 1.3/TCP profiles, eight controlled
covers, and message lengths of 40 and 200 characters.

Each of three runs contains 80 matched FHAM/control pairs per profile. Messages
and control bodies use different deterministic seeds in each run. A logistic
regression model is trained on two complete runs and tested on the held-out
third run; this leave-one-run-out split is repeated three times. The classifier
uses either byte/record-size features or those features plus relay read-chunk
and timing features. Matched pairs remain together in every test fold.

## Results

Each profile contains 240 pairs (480 TCP sessions) across the three runs.

| Profile | FHAM marker, FHAM/control | Equal directional byte totals | Equal TLS record-length sequences | Size/record AUC | Held-out relay-feature AUCs |
|---|---:|---:|---:|---:|---:|
| Raw TCP | 240/0 | 240/240 | n/a | 0.500 | 0.461, 0.498, 0.481 (mean 0.480) |
| TLS 1.3/TCP | 0/0 | 240/240 | 240/240 | 0.500 | 0.514, 0.536, 0.514 (mean 0.521) |

The relay-feature AUCs are reported in the FHAM-positive score orientation.
Each held-out run had 80 pairs. All six paired-bootstrap 95% intervals include
0.50: raw TCP (0.379--0.544, 0.411--0.583, 0.401--0.561) and TLS 1.3/TCP
(0.423--0.609, 0.447--0.622, 0.428--0.600). The measured timing and
read-chunk features therefore did not provide stable separation in this
matched local test.

Raw TCP exposes the versioned FHAM marker: the marker detector found all 240
positive streams and none of the 240 matched HTTP controls. TLS 1.3 concealed
the marker in all 240 positive streams. For TLS, every matched pair had the
same TLS record-length sequence in both directions and equal directional byte
totals.

The request volume still reveals message length. A 40-character FHAM request
uses 368 raw TCP bytes and 720 client-direction TLS bytes; a 200-character
request uses 1,008 raw bytes and 1,360 TLS bytes. Its HTTP control has the same
respective byte totals by construction. The size-only classifier therefore
cannot identify which application generated the matched exchange, while an
observer can distinguish the tested message-length groups by total volume.

## Interpretation

The experiment measures actual TCP streams observed at a local transparent
relay, rather than packet traces generated by a packet builder. It directly
tests marker exposure and a grouped classifier against length-matched HTTP
traffic on the same TLS stack. It does not measure TCP segment boundaries or
traffic from remote endpoints. The next extension for the full communication
chain is to compare FHAM flows with unmatched, mixed application traffic and
additional client/TLS stacks using packet captures from the deployment
network.

## Reproduction

Run three independent socket experiments and the held-out-run classifier from
the repository root:

```powershell
python scripts/socket_tls_detectability_pilot.py --run-id rep1
python scripts/socket_tls_detectability_pilot.py --run-id rep2
python scripts/socket_tls_detectability_pilot.py --run-id rep3
python scripts/evaluate_socket_tls_generalization.py
```

The relay runs entirely on loopback and requires no packet-capture driver.
Outputs contain per-flow aggregate timing, byte, read-chunk, and TLS-record
features only:

- `results/socket_tls_detectability_flows_rep1.csv` through `rep3.csv`
- `results/socket_tls_detectability_summary_rep1.csv` through `rep3.csv`
- `results/socket_tls_generalization.csv`
- `scripts/socket_tls_detectability_pilot.py`
- `scripts/evaluate_socket_tls_generalization.py`
